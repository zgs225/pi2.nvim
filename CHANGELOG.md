# Changelog

## 2026-11-12

- **ADDED:** A `worktree=<name>` **start flag**: `:Pi worktree=<name>` / `:PiNewTab worktree=<name>` (and `pi.worktree_open()`) open a **fresh** conversation in an **existing** managed worktree instead of creating a checkout. The name resolves under `<repo>/.worktrees/<name>` (completion offers the repository's names); from Lua `cwd` wins over `name` and must itself be a linked worktree (the main checkout is refused), and `new_tab` defaults to `true` — `:Pi` uses the current tabpage and refuses while that tab already runs a session, because two processes cannot own one tab. Nothing is created and nothing is removed: an unknown name is an error that points at `:PiWorktreeNew <name>`, and a failed process start only closes the empty scratch tab, leaving the checkout (and the work in it) untouched. `:PiContinue` / `:PiResume` reject the flag because they pick their own workspace, and a worktree's recorded session binding is written only when it has none, so opening a second session there never steals the first one's binding. `pi.worktree_open(opts, cb)` joins the `pi.worktree_*` API. See doc/usage.md, doc/worktrees.md#opening-another-session-in-an-existing-worktree and doc/api.md.
- **ADDED:** `:PiResume` now **partitions its sessions per checkout** once the picker spans two or more of them: a `󰙅 <worktree>` title row for each linked checkout and the project name for the main checkout, with that checkout's sessions underneath, newest first (partitions ordered by their newest session). Rows lose the per-row `· 󰙅 <name>` suffix — the title carries the context — and a single-checkout list keeps exactly the flat shape it had. Typing in the prompt filters case-insensitively over the row text, the partition title, the worktree name and the checkout path, and matched sessions stay under their partition title (grouping is decided before filtering, so narrowing to one checkout still shows its title). Title rows are inert: `<CR>` / `o` / `t` / `<C-t>` step to the next session row, `<C-x>` deletes no titles, and the `vim.ui.select` fallback reopens the picker when one is picked. The row model lives in a pure module (`pi.sessions.resume_layout`) shared by both picker backends. See doc/sessions.md#resume-picker and doc/worktrees.md#resuming-across-worktrees.
- **ADDED:** `W` in `:PiSessions` starts a **new** session in a new tab rooted at the checkout of the row under the cursor — the worktree group it is listed under (a group header or any member row, the main checkout included), else the session's own worktree, else its cwd — and warns instead of opening a tab when that checkout no longer exists. See doc/sessions.md#sessions-overview-pisessions.

- **FIXED:** The first `<leader>ap` after a Neovim start froze the editor for **5–9 s** on a machine with a large `~/.pi/agent/sessions` tree (measured on the author's tree — 2.2 k sub-session rows over 1.8 GB of transcripts — 7.0–9.0 s down to 0.46–0.56 s). The startup status rebuild decoded **every line of every transcript twice**: once per manifest row through `Read.infer_run_status` (a full `read_jsonl`, which decodes payloads nobody asked for) and once per file through `History.parse` while building its id→path index. Three changes remove the byte-scaling work: session ids now resolve from the `<timestamp>_<id>.jsonl` filename convention (one `glob` plus a one-line header check per hit instead of a full parse per file, with the parse-based scan kept as the fallback for renamed files), `infer_run_status` / `last_turn` read the transcript from its **end** via a new tail reader (`open_tail` in `pi.subsessions.read`: backwards 64 KiB windows that hand a split line to the next, older window instead of re-reading, and lines carrying neither a `message` nor a `tool` payload skipped before the JSON decode), and a row whose transcript mtime still matches its recorded `last_active_at` is not re-inferred at all — the status booked from that file cannot have changed, except for a row left `active` by an unclean shutdown, which is still inferred. Cold cost (the first start after upgrading, every row stale once) lands at ~1.4 s; steady state is ~0.5 s. Regression-covered by `tests/subsessions_read_spec.lua` (decode counts bounded by the tail window; huge, truncated and CRLF trailing lines) and `tests/subsessions_rebuild_spec.lua` (no transcript parse on the fast path, header-id verification, non-conventional filename fallback, mtime short-circuit). The budget is now an explicit rule in `AGENTS.md` and `.agents/skills/develop/references/architecture.md`; see doc/troubleshooting.md#the-first-open-is-slow.
- **FIXED:** A sub-agent whose model call failed was reported to the parent as a **successful** run with an empty reply. A provider rejection (quota exhausted, invalid API key, rate limit, dead network) is persisted by pi as an assistant message with `stopReason: "error"`, no content and the reason in `errorMessage`; the settle path inferred the outcome from the manifest's `failed` status instead — which only spawn-time failures ever set — so the batch item settled `ok` with `output = ""`, the batch reported `completed`, the manifest said `completed`, and `dispatch_subagents` / `wait_subagents` handed the orchestration agent a silent success it had no way to act on. The turn's own stop reason is now the source of truth (`Read.last_turn` reads text, stop reason and provider error in one pass, with the live `message_end` mirror on the session as the file-less fallback): a failed run settles its item as `failed` with the provider message in `error` (batch `failed`, or `partial` when siblings succeeded), keeps any partial text in `output`, and records `status = "failed"` plus a new `last_error` in the manifest — which `list_subagents` returns as `error`, `read_subagent` shows as `(error: …)` on the projected turn, `Batch.rebuild` restores after a restart, and the startup status rebuild / idle reaper now infer from the same stop reason (an aborted turn also stops being inferred as `completed`). A user-spawned child injects `[Sub-session "x" failed] …` / `[子会话「x」失败] …` instead of going silent, the child process stays alive and reusable, and the failure policy is unchanged otherwise (`cancel_siblings_on_fail` now actually fires, because a quota failure is finally a failure). Two adjacent gaps in the same class were closed: a rejected prompt no longer discards the backend's reason (`failed to send task to sub-session: No API key found for …`, `prompt failed: …` instead of an opaque message), and `Manifest.patch` can now delete a field (`Manifest.REMOVE`) so a later successful run does not inherit a stale `last_error`. Regression-covered by `tests/subsessions_child_settled_spec.lua`, `tests/subsessions_read_spec.lua`, and the real-backend e2e `make e2e-subagent-failure` (`scripts/e2e/subagent_failure.lua`: real `pi --mode rpc` child against a local fake provider answering `429 insufficient_quota`, asserted against the item, the batch, the manifest and the child's JSONL). See doc/sessions.md#failed-runs, doc/extensions.md and doc/troubleshooting.md#sub-agent-failed-quota-auth-or-network-error.

- **ADDED:** A **reporting contract** for sub-agent reports — four static rules in the child worker note (`extensions/subagent-child.ts`) plus a lenient parser on the host side. Three failure modes had nothing to stop them: a child that wrote its report to a file and pointed at it delivered nothing (the parent reads the last assistant message only and opens no file it was not asked to), one that quoted relative paths handed the parent paths that resolve against the *parent's* cwd, and one that narrated the investigation before the conclusion had the outcome skimmed off the top. The note therefore now says: report in the last message, never in a file you point at; absolute paths; outcome first, then evidence, under roughly 200 words unless detail was asked for; and close with exactly one `STATUS: ok` / `STATUS: blocked` / `STATUS: failed` line, using `blocked` (and saying what you are stuck on) when unsure — still a byte-constant array join, so the prompt cache is untouched. On the host, `split_report_status` inspects the last non-empty line of a user-spawned child's final message (case-insensitive `STATUS:`, one of the three values) and `completion_report` moves the outcome into the notice header as `[Sub-session "x" completed: blocked] …` / `[子会话「x」已完成：blocked] …`, dropping the marker line from the body; agent-spawned children keep the synchronous tool-result path and get no notice at all. Two things are easy to misread: with no marker — or an unknown value, or a marker with nothing above it — the output is byte-for-byte what it was before, since the host never invents an `ok` out of silence; and a `STATUS` value is the child's **self-declaration**, not a verification result, so the parent still checks the evidence (runs the test, opens the file) before trusting a sibling's `ok`. See doc/sessions.md#reporting-contract and doc/extensions.md.
- **ADDED:** Child sub-sessions can be given a **tool allowlist** — `subagent.tools` as a default for every child, or `tools` on a `dispatch_subagents` spawn item for one of them — forwarded as pi's `--tools read,grep,find,ls`. A prompt could not do this: a child told to "only read" still had `bash` and the edit tools declared, and reached for them as soon as that was convenient, so a read-only scout (or a worker that must not edit or spawn its own children) was a request rather than a restriction; the flag removes those tools from the list the model is handed. Precedence is item `tools` → `subagent.tools` → `nil` (inherit every tool, the old behavior and the default — the key is deliberately absent from the defaults table, where a `nil` default cannot be expressed). Two sharp edges: the list **replaces** the child's whole tool selection, so it must name every tool the child needs (an empty array is rejected instead of meaning "no tools"), and pi's `--tools` only filters the tools declared to the model, so MCP tools stay callable regardless. `:PiSubNew` has no tools field, and a `{ target, message }` reuse item rejects `tools` like `name` / `model` / `thinking_level` because the revived child keeps its own configuration. For revive the allowlist is persisted in the manifest's `config.tools`, so `:PiSubSwitch` and `dispatch_subagents({ target, message })` bring a reaped child back with the same restriction; a manifest written before this feature has no such key and revives unrestricted, and a corrupt value degrades to "inherit every tool" with a warning instead of blocking the revival. `cli.args`' own `--tools` / `-t` is stripped from child command lines in favour of the resolved allowlist, with a one-time warning (`subagent.tools overrides --tools from cli.args for child processes`); the parent process keeps the flag. The orchestrator system-prompt note gained one static sentence pointing at `tools: [...]` for read-only children ("a prompt alone will not stop it"), still byte-constant so the prompt cache is untouched. See doc/configuration.md, doc/sessions.md#constraining-a-childs-tools and doc/extensions.md.
- **ADDED:** ANSI colour rendering for tool output. Terminal control sequences in a tool result are no longer written to the buffer verbatim: SGR colour codes become real extmark highlights (`lua/pi/ui/chat/ansi.lua`), so `ls --color`, `git status --color`, `grep --color`, pytest and cargo output is coloured in the chat instead of flat. 16-colour, 256-colour and 24-bit values plus bold/dim/italic/underline/strikethrough/reverse all map to generated `PiAnsi*` groups, resolved through the colorscheme's semantic hues (`DiagnosticError` for ANSI red, `DiagnosticOk` for green, …) with the xterm palette as fallback; the groups are re-resolved on `ColorScheme`. Spans sit at `priority = 300`, above the block's `PiToolOutput` base, and are carried across `<Tab>` — a collapsed block re-colours the output tail it duplicates. Terminal titles, cursor movement and line erases are dropped rather than emulated, and a `!` block is unaffected because the backend already strips ANSI before streaming it. No option: colouring is on by default and self-disabling — a failed highlight/extmark call turns the renderer off for the session and blocks keep rendering plain text. Regression-covered by `tests/ansi_spec.lua`, `tests/ansi_render_spec.lua` and the e2e `tests/ansi_render_e2e.lua`. See doc/usage.md#terminal-colours-ansi and doc/highlight-groups.md#terminal-colours-in-tool-output-piansi.
- **FIXED:** Terminal control characters used to leak into the history buffer: an escape sequence showed up as caret notation (`^[[1;32m`) and each ESC counted as **two display columns**, so widths were inflated everywhere they are measured — the `+N lines` / `…N lines` collapse thresholds, window-width elision, thinking previews and `gf` on a rendered path. `Tools.sanitize_text` now strips ANSI escapes (CSI, OSC, DCS, two-byte forms) and C0 control bytes, keeping `\t`, mapping `\r` to a space and `\z` to `␀` as before; every rendering path funnels through it, so copy, search and width math all see only the visible text.

## 2026-11-11

- **FIXED:** A background task's completion report was silently lost when the turn it arrived in was aborted. The report went out as a steering message and was marked delivered at *send* time, so pi discarding the steering queue on abort left the model unaware even though `:PiTasks` showed the task done — and the load-time `context` fallback, which exists for exactly this case, was excluded by that optimistic flag. Delivery is no longer fire-and-forget: a report now walks `pending → sent → confirmed`, where only `context` — the exact message list about to be sent to the model — confirms it, and anything still unconfirmed is injected there. The same fix covers a `wait_task` that is aborted before it returns: its claim on the result is released instead of consuming it.
- **CHANGED:** Mid-run completion reports now arrive at an actionable turn boundary instead of through the steering queue: the extension appends a `custom_message` entry at `turn_end` (else `agent_before_settle`) and asks for one continuation, so a model that ended its turn while a task was still running picks the result up in the same run. Entries are committed even when the turn ends in an abort, which is what makes the report survive Esc; an aborted run requests no continuation, so aborting still just stops. An idle completion still starts a turn immediately. Several tasks finishing in the same window now share **one** message (a single task keeps its 40-line / 4 KiB output tail; a batch carries one status line per task and omits the tails), so a burst of completions cannot flood the context.
- **ADDED:** `make e2e-bg-delivery` — a real-pi end-to-end suite (`scripts/e2e/bg_tasks_delivery.lua`) that drives `pi --mode rpc` with the bundled extension and checks the transcript for the idle-wake, turn-boundary, aborted-run and aggregation paths, asserting each report appears exactly once. Needs the pi binary and a provider, so it stays out of CI.

- **ADDED:** `wait_task` — a blocking wait for background bash tasks, so the agent stops using `sleep` to wait. The `bg-tasks` extension now registers `wait_task(task_id, timeout_ms?)` (default 120 s, max 30 min) next to its `bash` override: it stays attached to the task inside pi, is event-driven (a task that exits in 3 seconds returns in 3 seconds, no polling), and returns the task's output plus exit code. Its own deadline does **not** kill the process and is reported as `[still running]`, explicitly labelled as not a failure. The tool has its own chat renderer (the task's command, its id and the attach window as the block body, the waited task's output as the result body), so a backgrounded command's output is readable in the conversation and not only in `:PiTasks`. Completion is delivered exactly once via an observer lease: a call attached at exit consumes the result, so a waited-on task produces no duplicate wake.
- **ADDED:** A dedicated hourglass icon for `wait_task` blocks (`nf-md-timer_sand`, `0xF051F`) instead of the generic `labels.tool` fallback — blocks are scanned by their glyph, and a generic dot made a blocking wait look like an unrecognized tool. Every other tool keeps its icon.
- **CHANGED:** A foreground `bash` command that outlives its timeout is no longer killed. Both the foreground and the background path now share one spawn routine and differ only in how long the call stays attached: the `timeout` parameter (default 2 minutes, clamped to 1s…10min) is the attach window, and a command that exceeds it keeps running as a background task whose id, output file, and output so far are returned as `[still running]`. Quick commands are unchanged (same output, pi's 50 KiB / 2000-line truncation, `Command exited with code N`), abort still kills the process group, and the log of a command that finished inside its window is deleted unless the truncation footer points at it. The model therefore no longer has to pre-emptively background a command it fears will time out — which removes one of the main reasons it reached for `sleep`.
- **CHANGED:** `wait_task` blocks are readable at a glance instead of showing a task id. The body now leads with the command the task runs, followed by the id and the attach window (`npm run dev · b3f2a1 (timeout 30s)`) — the command comes from the task registry the extension's `started` event populates, so it is there for a live block and for one replayed from a session file, with the bare id as the fallback when a session was resumed after pi restarted (flattened, elided at 80 columns). The header carries the outcome as status text: `still running` for a deadline hit (so the block is not misread as a failed wait), `exit 1` / `signal SIGTERM` for an abnormal exit, and nothing on a clean exit, where the result body already reports `exited with code 0`.
- **CHANGED:** `poll_subagents` / `wait_subagents` rows name the batch instead of showing its id. Both render inline (one line, no body), so `batch …123456` was the only thing tying a row to the work it waited on: the row detail now lists up to three item labels read from the persisted batch record, elided as `+N` (`auth-review, schema-fix, docs-sweep, +2`), with `batch …123456` kept as the fallback when the record is gone, and `wait_subagents` also shows the wait window (`… (timeout 300s)`). The header status appends the items that did not come back cleanly (`5/5 partial · ✗ schema-fix, ✗ docs-sweep`) — the counters alone said how many failed but never which. `dispatch_subagents` and `list_batches` are unchanged.
- **CHANGED:** Wording that makes waiting unnecessary, in three places. The overridden `bash` description, every result that starts or hands off a task, and the new tool's `promptGuidelines` now say the same three things: never `sleep` and never poll a task's output file; if there is other work, do that; and if the task's result is all that is left, **ending the turn is the correct move** (the wake report starts a new turn) or call `wait_task`. The wake report itself now begins with `[SYSTEM NOTIFICATION - NOT USER INPUT]` and inlines the last 40 lines / 4 KiB of output, so a model woken with a finished task neither mistakes the report for a human message (or for approval of whatever it proposed before going quiet) nor needs a follow-up read. Prompt rules alone do not fix this — Claude Code spent a year adding "do not poll" lines before shipping a wait tool — which is why the affordance and the wording land together.
- **FIXED:** Foreground bash commands now get pi's bin directory prepended to `PATH` (derived from `process.execPath`), matching core's spawn env; previously only the background path existed and it inherited the parent `PATH` unchanged. A custom `shellPath` from pi's settings.json is still resolved by core's exported `getShellConfig()` rather than read from settings.
## 2026-11-06

- **ADDED:** Git worktree isolation for sessions. `:PiWorktreeNew [name]` / `pi.worktree_new()` starts a fresh conversation whose `pi --mode rpc` process runs with `<repo>/.worktrees/<name>` as its cwd (a linked worktree on a **detached HEAD** at the repository's `HEAD`, recorded as its base commit), in a new tabpage — the conversation you ran it from keeps running untouched. `:PiWorktreeFork [name]` / `pi.worktree_fork()` does the same with `--fork <session file>`, so the conversation continues in the checkout while the parent session file is untouched (the sessions list marks it `↳ forked from <name>`); it is refused while streaming, for an empty conversation, and when `cli.args` carries a session-selecting flag (`--continue`/`-c`, `--resume`/`-r`, `--session`, `--no-session`). A session that already runs in a worktree refuses to create another one (no nesting), and a failed process start releases the fresh checkout instead of leaking it. Naming: the optional argument (1–64 chars, `[A-Za-z0-9._-]`, no leading `.`), else a generated `wt-<YYYYmmdd-HHMMSS>-<pid>-<seq>` (timestamp alone repeats within a second).
- **ADDED:** `:PiWorktreeBranch <branch>` / `pi.worktree_branch()` attaches a branch to the current worktree session (`git checkout -b`, or the existing branch of that name), since the checkout starts detached. `:PiWorktreeApply [name]` / `pi.worktree_apply()` opens the worktree's patch (base commit → now, untracked files included) in the shared diff-review panel and applies it to the **main checkout's working tree** only on an explicit `a` accept — no index change, no commit, and an atomic `git apply`, so a conflict leaves both checkouts as they were. If a π session is running in the main checkout, that accept asks for confirmation first (naming the checkout and the session, since its agent may be using those files mid-turn): cancelling writes nothing, and confirming re-checks immediately before the write so a *different* session started in the meantime aborts the apply instead of being written under. `:PiWorktreeShip [name]` / `pi.worktree_ship()` prefills the target session's prompt with a plain-text ship brief (absolute path, base/HEAD, dirty/ahead state, branch/commit/push/PR/conflict requirements) and **never sends it**. `:PiWorktreeRemove [name]` / `pi.worktree_remove()` refuses while any live π process runs in the checkout, shows a confirmation naming the dirty/ahead risk, writes a patch snapshot first (aborting the removal if that fails), then `git worktree remove --force` + `prune`. See doc/worktrees.md.
- **ADDED:** Repository hygiene for new checkouts. `/.worktrees/` is appended to the repository's `.gitignore` when git does not already ignore it (never staged or committed), a `.worktreeinclude` file at the repo root copies matching **git-ignored** files into each new worktree (intersection with ignore rules, `.worktrees/` itself excluded, 20 000-file cap), and the new `worktree.setup_cmd` array runs once inside the fresh checkout (no shell, cwd = worktree) before the session starts — a non-zero exit keeps the checkout but fails the creation.
- **ADDED:** Cleanup and snapshots. Closing a session's process releases its worktree, deleting the directory only when it is **clean and not ahead of its base commit**; a dirty/ahead checkout is kept and the path is reported, so nothing is lost. A release snapshots before deleting like every other removal: a clean checkout's patch is empty, so it leaves an **empty patch plus its `.patch.json` sidecar** behind — a record of the checkout (name, path, base, HEAD, time) that keeps its session discoverable on resume — and if that snapshot cannot be written the checkout is **kept** instead of deleted. Snapshots (`.git/pi2-worktree-snapshots/<name>/<timestamp>.patch`) are written by `:PiWorktreeRemove` and by `pi.worktree.remove` and are never garbage-collected. Patch capture is all-or-nothing: >20 000 untracked files, or an untracked path a patch cannot represent (a directory holding its own git repository — a nested clone, vendored repo or submodule checkout), fails the capture with a message naming the path, so the snapshot is never truncated and the removal (or `:PiWorktreeApply`) is refused instead of silently dropping that work. New config: `worktree.setup_cmd` (default `nil`), `worktree.isolate_subagents` (default `true`), `worktree.snapshot_before_remove` (default `true`).
- **ADDED:** Automatic integration of sub-session work. When an isolated child settles, `pi.worktree_integration` captures its patch (base → now, untracked included), writes a durable snapshot (`<timestamp>.patch` + a `.patch.json` sidecar naming worktree/repo/base/HEAD/time) and applies it to the **parent checkout's working tree** — never the index, never a commit — only at a safe window: the parent blocked in `wait_subagents` (its turn suspended inside that tool call) or idle. Otherwise the row parks as `queued` and retries on the next readiness signal (wait start/end, turn end, resume); a busy parent never toasts. Aborted **and failed** runs are never integrated; a modified Neovim buffer the patch would touch or a second live session in the target checkout also blocks the write. Applying is checked, not blind: `git apply --check` / `--reverse --check` decide `clean` (apply), `already` (record it and never write twice) and `conflict` (nothing written), the patch is re-probed after the write before success is recorded, `patch_sha` prevents replay, and a base commit that drifted from the target `HEAD` is a conflict rather than a textual apply. On a conflict (or stale base) the still-running child can be asked **once** to rebase onto the parent's `HEAD`, resolve in its own checkout, test, and report back (`worktree.integration.auto_resolve`, `max_attempts` default 1; `0` disables), after which the row stops in `needs_attention`. State lives on the manifest row and is written before the first write, so a restart reconciles it (`applying` → probe → applied/queued/needs_attention, `queued` → re-enqueued, `resolving` with a dead child → stopped). A reused checkout integrates only its own new work (delta from the recorded `head_sha`, or a plain capture when the base changed), and never replays an earlier patch (`needs_attention:delta_baseline_missing`). The applied checkout is deleted only when nothing else would be lost — no other live process rooted there, child process quiesced, snapshot present, no ignored content, generation unchanged, and a fresh re-capture still hashing to the integrated patch — otherwise it is kept with a reason. Every event is written into the parent chat as a persistent `󰙅 …` history line (new `PiWorktreeIntegrationIcon` / `PiWorktreeIntegration` groups), and a child row in `:PiSessions` shows one integration glyph (`⧗` queued, `…` applying/resolving, `✓` applied, `!` needs attention; new `PiSessionsListIntegration{Queued,Running,Applied,Attention}` groups) — rows with a pending or attention-needing integration stay visible even when their completion was already read. See doc/worktrees.md#automatic-integration.
- **ADDED:** Retention for applied child checkouts. `worktree.integration.keep_count` (default 15) is a soft cap across every workspace: once the managed total exceeds it, the oldest **`applied` + verified-present + inactive + unpinned** checkouts are removed (and re-probed at fire time). Parked (`queued`/`applying`/`resolving`), `needs_attention`, deliberately kept and unverifiable checkouts count toward the total but are never removed for quota, and snapshots are never deleted. It runs after the startup reconcile and after integrations settle.
- **ADDED:** Cross-worktree resume. `:PiResume` now lists the sessions of Neovim's cwd **and of every managed worktree of the same repository** (`Worktree.list` plus `Worktree.snapshot_worktrees`, only when the repo has a `.worktrees/` directory or a snapshot store), labelling those rows `· 󰙅 <name>` and restarting the process **in that checkout** when one is opened (closing the current process first when the cwd differs, refusing while it streams). Deleted-but-recoverable checkouts are enumerated from the snapshot store too — including the empty patches a clean release leaves, so their sessions stay resumable. A checkout that vanished is recovered before any process is started: an applied integration record (or snapshot sidecar) recreates it at the repository's current `HEAD`; an empty snapshot patch recreates it at the recorded base and applies **nothing** (a no-op restore); otherwise the latest snapshot recreates it at the recorded base and the patch is applied inside it; with neither, the picker reports the failure and never silently opens the transcript in the main checkout. `:PiContinue` stays cwd-scoped.
- **ADDED:** Sub-sessions run in their own worktree by default (`worktree.isolate_subagents`). Each spawned child gets a `sub-<timestamp>-<n>-<pid>` checkout instead of the parent's, so parallel children cannot overwrite each other's edits; a child of a parent that already runs in a worktree inherits that cwd instead (never nested), a revived child reuses the worktree recorded on its manifest row while it exists (a checkout that was already released is recreated at its recorded path, because a resumed transcript refuses a missing working directory), and release deletes only clean checkouts, so dirty child work survives a close/revive cycle. The idle reaper's sweep also releases checkouts recorded for children no live session owns any more (Neovim restarts). Bookkeeping follows the owner: a child's row lives in the **parent session's workspace** manifest (recording the child's own transcript path and its checkout) while its JSONL lives in its own workspace, and row lookups search across workspaces — so close, revive, rename and the reaper keep working when Neovim's cwd is in another checkout.
- **ADDED:** Worktree visibility. The chat history title carries a worktree badge (`󰙅 <name>`, with a trailing `*` while dirty/ahead) in both layouts, rendered in the warning color with a `⚠` prefix when the session's cwd differs from Neovim's (the normal case for a worktree session). `:PiSessions` groups rows under worktree headers (`▾ 󰙅 name (n) · ~/path`, where `(n)` is the group's structural size — parent rows plus their sub-sessions, unaffected by folding a parent inside the group) once the list spans two or more distinct worktrees, folds a whole group with `<Tab>`/`za` (`zM`/`zR` for all), names the worktree on rows inside a group, and marks worktree forks; `R` re-detects worktrees. New highlight groups: `PiChatHistoryWorktree`, `PiSessionsListWorktree`. Single-worktree and non-git lists render exactly as before.
